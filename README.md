# Mock SMS Gateway API

A small FastAPI project that simulates how an SMS/CPaaS gateway (similar to 2Factor) handles sending messages, checking delivery status, and listing message logs.

This project does **not** send real SMS messages — it simulates realistic gateway behavior (async acceptance, delivery outcomes, common failure reasons like DND blocks and invalid numbers) to demonstrate understanding of how such APIs actually work.

## What it does

- Accepts a request to "send" an SMS and immediately responds with an accepted status (mirroring real-world async SMS APIs, where final delivery isn't instant)
- Simulates a delivery outcome (delivered / failed) with realistic failure reasons
- Lets you check the delivery status of a specific message by its ID
- Lets you list all sent messages, with optional filtering by status

## Tech Stack

- **Python 3**
- **FastAPI** — for the API framework, request validation (via Pydantic), and auto-generated docs
- **Uvicorn** — ASGI server to run the app
- In-memory storage (a Python dictionary) instead of a real database, to keep the project simple and dependency-free

## How to Run

1. **Clone the repository / download the files**

2. **Install dependencies:**
   ```bash
   pip install -r requirements.txt
   ```

3. **Run the server:**
   ```bash
   uvicorn main:app --reload
   ```

4. **The API will be running at:** `http://127.0.0.1:8000`

5. **Interactive API docs (auto-generated by FastAPI):**
   Visit `http://127.0.0.1:8000/docs` in your browser — you can test every endpoint directly from there, no Postman needed.

## API Endpoints

### 1. Send an SMS
```
POST /send-sms
```
**Request body:**
```json
{
  "phone_number": "9876543210",
  "message": "Your OTP is 4321"
}
```
**Response (202 Accepted):**
```json
{
  "message_id": "83c82877-aaaa-4eda-8cfe-b005f0a32a45",
  "phone_number": "9876543210",
  "status": "accepted",
  "timestamp": "2026-09-19T12:15:24.273389+00:00"
}
```
**Validation error (422):** if `phone_number` isn't exactly 10 digits.

---

### 2. Check Delivery Status
```
GET /status/{message_id}
```
**Response (200 OK):**
```json
{
  "message_id": "83c82877-aaaa-4eda-8cfe-b005f0a32a45",
  "phone_number": "9876543210",
  "status": "delivered",
  "error_reason": null,
  "timestamp": "2026-09-19T12:15:24.273389+00:00"
}
```
If the message failed, `status` will be `"failed"` and `error_reason` will show a simulated reason (e.g., `DND_BLOCK`, `INVALID_NUMBER`, `DLT_TEMPLATE_MISMATCH`, `CARRIER_ERROR`).

**Not found (404):** if the `message_id` doesn't exist.

---

### 3. List All Messages
```
GET /messages
GET /messages?status=failed
```
**Response (200 OK):**
```json
{
  "count": 2,
  "messages": [ ... ]
}
```
Supports optional filtering by `status` (e.g., `delivered`, `failed`) via a query parameter.

## Testing with Postman

A ready-to-use Postman collection is included at `postman/SMS-Gateway-API.postman_collection.json`.

**To use it:**
1. Open Postman → Import → select the JSON file
2. Make sure the server is running locally (`uvicorn main:app --reload`)
3. Run "Send SMS" first, copy the `message_id` from the response
4. Paste it into the collection's `message_id` variable to test the "Get Message Status" request

## Design Notes / What I Learned

- Implemented the **async API pattern** used by real SMS/CPaaS gateways — the initial response only confirms the request was *accepted*, not that the message was *delivered*, since real delivery depends on external telecom networks.
- Used **Pydantic models** for automatic request validation — invalid input (like a malformed phone number) is rejected with a clear `422` error before any processing logic runs.
- Simulated realistic **failure reasons** (DND blocks, DLT template mismatches) based on how Indian SMS compliance actually works, rather than generic "error" messages.
- Chose in-memory storage over a real database to keep the project self-contained and easy to run, while keeping the code structured so a real database (e.g., MySQL) could be swapped in later.

## Possible Future Improvements

- Replace in-memory storage with a real database (MySQL/PostgreSQL)
- Add a webhook mechanism to push status updates instead of requiring a status check
- Add authentication (API key) to protect the endpoints
